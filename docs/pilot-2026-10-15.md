# Fixed-suite pilot — October 15, 2026

Five runs were launched with one frozen configuration. Four produced complete evidence; one stopped after a provider error left usage unknown. This is a short-term pilot, not a control baseline, a release approval, or a measurement of all possible requests. No limits or acceptance targets were fitted to these results.

The four complete runs have 92.8–94.8% confirmed passes (576/612 attempts combined). The repeated cases and simultaneous runs are not independent samples of arbitrary user requests; that aggregate is descriptive, not a population confidence claim.

Run 4 received an `InternalServerError` while grading `approved-then-ask`, attempt 1. The response supplied no usage. The pilot safeguard stopped subsequent calls, even though its $0.60 allowance had not been exhausted. Twelve attempts lack required judgments, including six scenarios stopped before execution. These are inconclusive; the seven already-established failures remain failures. The incomplete run is retained in history and cannot supply a failure-rate point. It was not replaced with a more convenient run.

The coding assistant inspected the recorded failures and a targeted sample of 15 confirmed passes: the first passing attempt of `read-fresh`, `which-call-v2`, and `no-email` in each run. This is an assistant review, not an independent human labeling exercise or fresh judge calibration. Raw verdicts were not changed.

| `overdue-first` | 8/15 | Handled the completed tasks but omitted the request to address overdue tasks. |

| `one-todo-for-both` | 1/15 | Added a duplicate after already renaming the existing task to cover both items. |

These 43 failed attempts overlap checks; the table counts attempts once per case. The completion judge’s last `overdue-first-in-context` finding (run 1, attempt 3) deserves owner review: the requested state was present, while the response omitted explicit acknowledgment. The “show the tasks” response in `check-if-still-needed` (run 1, attempt 1) also warrants checking the expected contract with the owner. Keep these distinctions visible rather than treating every failed grade as equally severe.

The sampled passes showed the expected freshness handling, clarification without writes, and refusal to email without adding tasks. They do not establish that other passing attempts are all correctly graded. No prompt or grader changes were made to improve these pilot scores.

## Conditions and reproducibility

- The five runs started together, each with six concurrent case workers. They therefore describe the same short period and shared provider conditions. They do not establish day-to-day stability.
- Agent and judge requested and reported `gpt-6-luna`, with Langfuse export disabled. The provider reported the default service tier and no system fingerprint. An alias is not proof of an unchanged backend.
- Simulated application date: September 24, 2026. Execution date: October 15, 2026. Fixed test dates are intentional.
- Each request had a 4,096-output-token cap, a 64 KB serialized-request limit, a 60-second timeout, and automatic SDK retries disabled. The largest reported completion was 362 tokens. These settings and the pilot wrapper’s hash are in the configuration; ordinary CLI runs with different settings form a different comparison period.
- Source snapshots, dependency versions, call usage and raw pre-grading checkpoints are saved locally. The code was uncommitted at measurement; a commit label alone cannot reproduce it. Later reporting and persona-only changes do not rewrite that snapshot.

## Cost and next collection

The five runs reported 7,853,647 input and 234,622 output tokens. The known portion of estimated standard API charges is $0.3886. The four complete runs cost about $0.077–$0.080 each at reported cache usage. Run 4’s total is unknown because one failed response had no usage. The separate conservative ledger, charging input without cache discounts and reserving for the failed response, accounts for $1.1096 across all five; it is not an invoice.

At the observed usage, 20–30 similar full runs would be roughly $1.60–$2.40 with similar cache behavior, or about $4.50–$6.80 using the conservative uncached accounting. These are planning estimates for this small fixed suite and model, not a guaranteed bill. A larger model, longer conversation, different grader, or retries changes the estimate. No further baseline collection was launched.

The earlier instrumented attempt used a different retry/budget configuration and stopped early. Its known token estimate is $0.0975; its conservative ledger is $0.6321. It is archived separately under `runs/preliminary/`. Its old harness classified six budget stops as application errors; those raw labels are preserved but must not be interpreted as application defects or combined with this pilot. An earlier complete 145/153 run had no token accounting and is also excluded from automatic comparison.

The retained records use the dated prices in [eval_costs.py](../eval_costs.py). Provider billing remains authoritative. The measured conservative allowances plus the small persona smoke run stayed below the agreed $5 exercise ceiling; the earlier uninstrumented run cannot be reconciled to a token invoice locally.

## Persona smoke test

One headless Priya session exercised three turns using the existing persona prompt, the real agent and a scratch list, with trace export off. It retained the conversation, state changes and offline HTML review. The final state showed Priya’s three chores, marked recycling done, and left roommate chores unchanged. The persona did not declare completion before the three-turn limit: this is a runner smoke test, not a successful-persona score or browser interaction test.

The 12 calls reported 20,460 tokens against a 20,000-token allowance. That expected overshoot illustrates why a between-call token allowance is not a hard billing limit. Conservative token accounting was $0.0033 rounded up. The visible persona player remains necessary to inspect actual screen behavior.

## Recommended next step

Review the ambiguous expectations and confirm labels before changing the judge. Prioritize clarification before writes and unwanted task creation, then measure one behavior change at a time. Keep current records as the previous configuration. Collect a longer, deliberately spaced baseline only after choosing the behavior and grading contract to monitor; do not spend the remaining credit merely to reach a run count.
