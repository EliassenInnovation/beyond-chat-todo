# Give the model clear tools and current evidence

The agent can only choose well from what it is given: the tools, their descriptions, and what each one returns. Most of the work of improving an agent is improving those, and checking that each change helps everywhere, not just where it was aimed.

## Make tool choices clear

**Improve the tools before adding rules or reviewers.** Expect to spend most of your effort here. Inspect the tool description, inputs and returned evidence before assuming another prompt rule will fix the problem. Anthropic reports the same for its own coding agent: "we actually spent more time optimizing our tools than the overall prompt." [32](https://www.anthropic.com/engineering/building-effective-agents) When the agent gets a job wrong, first read what it actually received from each tool: the tool's description, its inputs, and the result or error it returned. A tracing tool, such as Langfuse, makes this practical: it shows the tools the model had to choose from, each tool's description and inputs, and what each returned, in a form that is easy to review (see [evaluation](evaluation.md)). Is the tool's purpose clear? Can the agent tell it apart from similar tools? Does an error say what to do instead? Fix those, and move predictable work and checking of inputs into code. [14](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions) Add a rule to the prompt, or another model to review the agent's answers, only for problems that remain, and check that each one is worth the time and complexity it adds.

**Tools are read together, so one change can affect other jobs.** The model receives tool descriptions alongside instructions, results and conversation history. Adding or rewording one tool can change its choices elsewhere. Evaluate affected jobs during development and run the broader suite before accepting a behavior change.

**Scale testing to the change.** Run offline checks and focused visible cases while iterating, then the broader visible suite before accepting the change. Use held-out cases after the fix is frozen. Repeated baseline collection estimates variation in a stable configuration; it is not a requirement to run twenty suites for every edit. The [evidence chapter](../guides/evaluation-results.md) explains the distinction.

**Tool order may change which tool the agent picks.** Studies find that some models prefer tools listed earlier, especially when several tools fit a request about equally well. [33](https://arxiv.org/abs/2510.00307) Model vendors do not document this, so it can change with any new model or update. Do not depend on it: keep the set of tools small, avoid tools that overlap, and write descriptions that make the right choice clear. [34](https://www.anthropic.com/engineering/writing-tools-for-agents) [14](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions) Reorder tools only as a last resort.

**Put guidance where it belongs.** Keep the agent’s role and priorities in its instructions, operation-specific meaning in tool descriptions, and result-specific limitations beside the returned data. Measure the effects of each change. There is no universal rule that one location is strongest for every model or task.

## Return facts and structured decisions

**Let the model and the application code each do their part.** You use an AI in an application because it can recognize what the user is trying to do and what matters to them. But an interaction with an agent often involves work that belongs in code: adding a group of numbers, analyzing a data set, confirming what was saved, giving the path to a setting. Asked for the combined balance of three accounts, the model works out which accounts the user means, and code adds them. A model asked to add numbers is usually right; a tested calculation in code gives the same answer every time, and that answer can be checked. This is why a chat app such as Claude or ChatGPT writes and runs Python when asked to analyze data. In an application, the application's own code meets the same need.

**Show the application's own text instead of asking the model to repeat it.** When the application already knows the right words, show them as the application's own text: the confirmation of what was saved, the path to a setting built from the screen's own labels, where a moved item used to be. "Where do I change my cancellation fee?" needs the model to work out which setting the user means. The path to it, "Settings → Payments → Cancellation fee," is already known to the application and should reach the user exactly as written. Asking the model to retype that text adds only a chance to get it wrong: even current models sometimes fail to copy text exactly, when it is well within what they can read. [35](https://arxiv.org/abs/2607.16072) Every such answer then needs a check of its own. When the application shows the text, the words are exactly what the application wrote, so they can be tested once in code like any other output, and what remains to test is whether the model picked the right setting.

**Use structured responses when code consumes a model's answer.** A judge's verdict, a persona's next action, and a guard's decision need named fields with defined types and allowed values. Use the provider's supported schema mechanism rather than trying to infer those fields from free-form prose. Validate the result in application code, including values and relationships that a schema cannot establish. A refusal, truncated response or invalid result is unavailable evidence, not a successful decision. The [model chapter](../guides/models.md) describes the sample's provider adapters.

**Let the agent name a whole group.** A request such as “every open ticket in this sprint” should be representable as a selector that application code resolves. This avoids having the model copy a long list of identifiers and accidentally omit members. Validate the selector, show the affected scope, and apply the same authority and transaction rules as other writes. Keep selectors general, rather than matching the wording of one evaluation case.

**Keep the prompt focused.** Use the prompt for the agent's role, its priorities, and how it should approach the work. Put formats and the details of each operation in the tool descriptions instead. State the priorities in order, plainly, and give the same order to any model that reviews the agent's answers. An investment assistant might put compliance first (it informs but never recommends an investment action), then accuracy, responsiveness, and brevity; a scheduling assistant might put never double-booking first. [5](https://www.microsoft.com/en-us/research/project/guidelines-for-human-ai-interaction/) The prompt guides behavior; only code enforces it (see [authority and recovery](authority.md)).

## Validate against current state

**Read before answering, from the source that owns the fact.** Before the agent makes a claim about the application's data, it should read that data with a tool, from the part of the application that owns it. The code that runs the agent can require the read; a prompt can only ask for it. If the read fails, the agent should say so and limit its answer. [9](https://arxiv.org/abs/2210.03629) The conversation records what was said, not what is still true, so read again whenever the data may have changed, including changes the user made on another screen.

**Give the agent the same warnings about old or missing data that the user sees.** If the application would show the user that data is out of date, missing, or could not be checked, through a date, a warning, or a dash in place of a value, its tool results should tell the agent the same thing. Otherwise the agent will state an old earnings date, or a missing value, as current fact.

**Check what the agent passes to a tool before changing anything.** The inputs to a tool come from a model, so they can be close but not exact, or refer to something that does not exist. Correct small known differences, such as a ticker typed in lower case; check that identifiers exist and values are allowed; and when an input could mean more than one record, reject it and say which records it could mean, rather than guess.

**Keep the conversation history true to what the user saw.** The agent reads the earlier conversation to decide what to do next, so that history has to match what actually happened. This matters most when anything between the agent and the user can change an answer, such as a reviewing model that rewrites it. Keep the version the user actually saw, and keep failed actions too. Otherwise, on the next turn, the agent may assume the user saw an answer they never received, or that a change was made when it failed.
