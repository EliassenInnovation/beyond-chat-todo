# Make room for the agent

An embedded agent needs a place in the application. Familiar chat controls provide a useful
starting point, but placement, size, and behavior should support the work people are doing.
Sometimes the conversation is the work. Sometimes it should help people reach a screen and
then leave that screen available to them.

This section offers an initial set of design choices to try. The public guidance linked
below provides established patterns; the Advisor examples illustrate particular choices,
not evidence that one layout works best for every application.

## Choose where it belongs

Start with what people need to see while using the agent. A conversation beside a document,
list, or form can let them refer to both without switching views. A bottom panel preserves
horizontal space but reduces the height available for the task. A floating window takes
less permanent space, but can cover the content or controls people need.

The todo sample uses a side panel. Advisor uses a bottom panel. Neither placement is a
requirement of the architecture. SAP's Joule guidance describes large, medium, and minimized
panels, and advises against a full-screen panel when people need to interact with content
outside the conversation. Its guidance supports choosing the panel size around the work;
it does not establish one universal placement. [SAP: Joule panel](https://www.sap.com/design-system/fiori-design-android/v25-4/joule/components/joule-panel)

Try the layout on a normal laptop, with realistic content. Check whether opening the agent
hides a field, compresses a table, or forces people to scroll repeatedly between a request
and its answer. Let people resize or minimize the conversation without losing it.

## Give the conversation the space it needs

Advisor illustrates two different situations:

- **“Take me to where I can edit my thesis for NU.”** The useful result is the thesis editor.
  The conversation stays minimized to one line because a larger chat response would add
  little information and compete with the editing task.
- **“MU has been dropping. I'm thinking of changing my sell rule.”** The person wants to
  discuss a decision. The conversation expands to provide room for questions and explanation.

These examples describe Advisor's behavior as reported by its developer. Automatically
choosing a panel size from the task is a design choice to evaluate, rather than a general
rule established by the sources reviewed here.

Keep expansion and minimization predictable. Give people a way to override the choice, and
keep their conversation available. Do not hide a question awaiting an answer, an error, or
an approval that requires attention. Microsoft's human–AI interaction guidelines recommend
making assistance easy to invoke and dismiss and timing it to the user's context.
[Microsoft: Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/)

## Offer relevant starting points

A blank input box can leave people unsure what to ask. Small clickable suggestions—often
called **suggestion chips**—can show useful requests for the current screen, selection, or
conversation. For example, a product page might offer “Check compatibility” or “Compare
with another product.” Only offer requests the agent can actually handle in that context.

Nielsen Norman Group recommends relevant prompt suggestions and describes examples that
change with the conversation. It also recommends making it clear that an assistant knows
what the person is looking at. [NN/g: AI chatbot design guidelines](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/)

Decide what clicking a suggestion does. It might fill the input so the person can edit it,
submit a request immediately, or start an application action. These are different interactions.
SAP's prompt library fills the input for editing before sending; Google's conversation-design
guidance describes chips that submit a response. Make the behavior apparent, and keep any
required execution checks and approvals in place.
[SAP: Working with conversations](https://help.sap.com/docs/joule/joule-work-621104a90a01407fbb2d1613db39a54d/working-with-conversations),
[Google: Suggestion chips](https://developers.google.com/assistant/conversation-design/chips)

Suggestions can be prewritten and selected by application state, generated by a model, or
selected from an approved set with model assistance. Those are implementation options, not
requirements of the visual pattern. Start with the simplest approach that produces useful,
accurate suggestions. Model-generated suggestions still need to respect available
capabilities, the current context, and the user's permissions.

## Learn enough about the user to help

Some assistance depends on knowing more than the current request. A financial application
may need to understand a person's goals, time horizon, and circumstances before it can
provide relevant guidance. A personal shopper may need clothing sizes, preferred colors,
style, and budget. Collect the information that matters to the task rather than assuming
preferences from demographic details.

There are two hypotheses here, and they need different tests:

1. **Relevant user context improves assistance.** Learning and recording a few fundamental
   facts—or using information already in the application—may improve the agent's responses
   and decisions.
2. **Gradual onboarding is a better experience.** Asking for information as it becomes
   useful may feel more natural than requiring several screens of questions before the
   person can begin. It could also become a series of unwanted interruptions. We have not
   established which approach works better, or in which situations.

These are proposed directions to investigate, not findings demonstrated by the todo sample.
Advisor previously included onboarding, but it was accidentally removed. That behavior
needs to be restored and tested before we present Advisor as a working onboarding example.

### Ask when the information matters

One design to test is to let people begin with useful work, then ask a focused question when
the answer would improve the current task. Explain why it is needed, record it with the
person's knowledge, and let them inspect and correct it. Avoid repeatedly asking for facts
the application already has, while giving people a way to update information that has changed.

Decide what “enough context” means for each kind of assistance. A shopper might browse
without a saved size, but a size-specific recommendation needs more information. When a
missing fact is essential, ask before proceeding; when it is optional, allow the person to
skip it and make the limitation clear. A gradual approach should not become persistent
nudging to complete a profile that the current task does not need.

An onboarding prompt could focus on learning the basics and helping the person get started.
An ongoing-assistance prompt could use established context without repeating that introduction.
Application state should determine which instructions apply. This is an application design
choice; persona tests can exercise it, but do not establish that it improves the experience.

### Test usefulness and experience separately

To test whether context helps, compare responses to the same tasks with relevant facts
available and with those facts missing. Have reviewers assess relevance, unsupported
assumptions, appropriate questions, and whether the task was completed. A good response
with missing information may be a question rather than an immediate recommendation.

To test the experience, let real participants try an upfront questionnaire and a gradual
approach on comparable tasks. Observe whether they reach a useful result, where they stop,
how often questions interrupt their work, and whether they understand why information is
requested. Ask about their sense of control and willingness to continue. Include returning
users to find out whether gradual onboarding becomes repetitive over time.

Personas can help find missed questions and failures to save or reuse information. They
cannot establish that real people find an interaction natural or less annoying. Keep the
simulated person's private background separate from what the application has learned.

!!! consider "Consider — what does the agent need to know?"
    Choose one task. Write down which user facts are essential, which would improve the
    result, and which are unnecessary. What does the application already know? When would
    asking for each missing fact help the person with the task in front of them?

## Keep the application and conversation connected

Show the result where the person will use it. Navigation should reveal the destination;
an edit should appear in the application. Chat can confirm what happened, explain a limit,
or ask for missing information. It need not repeat everything already visible on the screen.

Make it clear which item or selection the agent is working with, especially after the person
navigates elsewhere. Preserve manual controls so people can continue the task directly.
Evaluate the whole interaction: the screen, focus, scrolling, suggestions, and conversation,
as well as the words in the response.

!!! practice "Practice — sketch two interactions"
    Choose one request that should take the person to a control or complete a short action,
    and one that needs a conversation. Sketch what remains visible in each case, how much
    space the agent takes, and how the person can change that. Add one useful suggestion
    and state whether clicking it fills the input or submits the request.
