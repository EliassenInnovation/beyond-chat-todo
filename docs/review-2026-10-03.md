# evalbasics: open issues from the Beyond Chat review (2026-10-03)

The Beyond Chat paper (advisor repo, `docs/beyond-chat-*.md`, version 2.3-draft) uses evalbasics as
its main example. An outside review of the paper, and a check of this repo on 2026-10-03, found the
issues below. Line numbers are from that day and will drift; search by name.

Items 1 to 3 cost no model runs. Items 4 to 8 need runs.

## 1. `answered()` can hide a real failure (bug)

`evaluations/evals.py`, `answered()` inside the evaluator setup (about line 883). It loops over the turns the
person typed and returns `[]` (not graded) as soon as one turn's judge fails or returns `None`. A
turn after that one is never judged, so a real failure on a later turn is reported as "not graded"
instead of a failure.

Fix: judge every turn first. If any turn's verdict is `False`, return the failure (with its quote).
Only if no turn failed and at least one judge could not answer, return `[]`. Otherwise return a
pass. Add a test in `tests/test_main.py`: a conversation whose first turn's judge raises and whose second
turn is a real failure must score 0, not unavailable.

## 2. Show uncertainty beside each per-case rate

The run report and the evals page print per-case rates such as 5/5 or 10/10 with no interval. The
paper now says (section 6) that by the Wilson 95% interval, 5/5 is consistent with a true pass rate
near 57% and 10/10 with one near 72%, so a single case's before and after is a direction, not proof.

Add the Wilson 95% lower and upper bound beside each per-case rate in the report and on the page
(`evaluations/evals_page.py`), so nobody reads 5/5 as "fixed". Wilson: centre (p + z²/2n) / (1 + z²/n), half
width z·sqrt(p(1−p)/n + z²/4n²) / (1 + z²/n), with z = 1.96.

## 3. Keep each case in one place

A case's grading rules are spread over four places in `evaluations/evals.py`:

- `TOUCHES` (about line 672): which todos a case may change.
- `FIELDS` (about line 692): which fields it may change on them.
- `MAY_WAIT` (about line 699): cases whose change may wait for approval.
- `grade()` (about line 809): a special case for `tell-then-sure` ("sure" must be carried out: if
  the screen still shows all, the Active filter must be pointed at).

Move `touches`, `fields` and `may_wait` into each case's dict in `CASES`, and turn the
`tell-then-sure` branch into a case field that `grade()` reads generically. Then retiring or adding a
case means editing one entry, and the held-out rule (no shared words or structure) can be checked
against one place. The full suite should give the same verdicts before and after; compare a run of
each.

## 4. Check 6.9 gaps: held-out cases

Check 6.9 (implementation guide): each case found in use or by a persona has a held-out paraphrase
that has never been run while fixing, fails without the fix, and is retired once seen. Three gaps:

- **`holdout-undo-the-move` is still active** (`CASES`, about line 564) but has been seen. STATE.md:
  "holdout-undo-the-move is now seen (run with and without the fix): Option 2 needs its own fresh
  one." Move it to `RETIRED` with that reason and write a fresh held-out case for `back-there`.
- **`when-is-it` (found in use) has no held-out case.** `holdout-refresh-memory` was retired
  ("run against a fix that was then reverted ... seen, so never reused") and not replaced. The same
  note says gpt-6-luna passes `when-is-it` without that fix. Decide: write a fresh held-out case, or
  record in the case why it does not need one.
- **`merge-keeps-count-v2` (found in use) has no held-out case.** Write one: the same job (two
  todos merged into one must keep the count), with other items and other words.

Each new held-out case counts only if it fails without the fix, so measure it once against the
commit before the fix and once against the current code, and record both numbers in its entry.
Never run it with `--case ... --held-out` while working on a fix.

## 5. Use a different model family for the judges

The agent and every judge default to gpt-6-luna (`todo/agent.py`: `EVALBASICS_MODEL`; `evaluations/judge.py`:
`EVALBASICS_JUDGE_MODEL`). A judge from the same family can share the agent's blind spots.

Run at least the claims judge on a different family: set `EVALBASICS_JUDGE_MODEL` and run
`judge_calibration.py --question claims`, and compare agreement, false alarms and misses with the
current 107/115 judgements. Keep whichever agrees better with the labels.

Also track how often Bob's samples disagree with the coding agent's labels in `judge_cases.json`
and the other case files (STATE.md: the coding agent labels, Bob samples and decides). Record the
number of labels sampled and the number changed, so the paper can say how good the agent's labels
are.

## 6. Measure tool-order dependence

`todo/agent.py` fixes the tool order (`TOOLS = REGISTRY.tools_for(..., order=[...])`, about line 59), and
the comments above it record order effects (delete requests 5/10 and 6/10 with `show_todos` before
the delete tool; 10/10 after). The paper now says each tool contract has to be clear on its own,
because the next tool added changes its neighbours.

Add an option to `evaluations/evals.py` (for example `--shuffle-tools`) that gives each attempt a random tool
order and records the order in the run report. Compare per-case pass rates with the fixed-order run.
A case whose rate drops when shuffled depends on its neighbours, and its contract needs fixing.

## 7. Report pass^k (new Check 6.10)

The paper now asks for pass^k beside the pass rate for jobs where consistency matters: whether all
k attempts at a case succeed, which is what a user repeating the job experiences. evalbasics
reports only per-case pass rates.

With `--repeat k`, add for each case whether all k attempts passed, and a suite-level count of cases
with all k passing. State k and the number of attempts in the report and on the page.

## 8. Run the suite with injected failures (new Check 6.11)

The paper now asks for the whole suite to be run with read failures, write failures and timeouts
injected, compared with the clean run. evalbasics has no injection.

Add an option (for example `--inject 0.2`) that makes a share of tool calls fail: a read that
errors, a save that fails without changing the list, a call that times out. Confirm the agent
reports each failure truthfully (`truthful` should stay at 100%) and that the saved list is right
when the job could still be done. Compare pass rates and pass^k with the clean run.
